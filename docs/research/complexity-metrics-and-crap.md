# Complexity metrics and CRAP: what's on offer, what the evidence says

Research for the owner's question of whether to add a code-complexity series to
the CI trend layer, prompted by one vendor blog post
([getotterwise.com](https://getotterwise.com/blog/understanding-crap-and-cyclomatic-complexity-metrics))
that the owner correctly flagged as not enough on its own. Every claim below is
tagged with how many independent sources back it; single-source claims are
marked and should be read as provisional, not settled.

**Short answer:** cyclomatic complexity (CC) is real and well-defined, but two
independent empirical lines (Shepperd 1988; Landman/Serebrenik/Vinju 2016) find
it mostly tracks lines of code, not something LOC doesn't already tell you.
Cognitive complexity is a deliberate, documented fix for CC's specific
counting failures, but it is SonarSource's own metric with no independent
replication found. CRAP's exponents (complexity², coverage³) were explicitly
**not** calibrated — the original authors called their formula "experimental"
and the threshold of 30 a starting guess. Two recent 2026 studies show
LLM/agent-written code trending worse on these metrics under iteration, in a way
human code in the same corpora does not. Recommendation is in the final
section.

## 1. The metrics

### Cyclomatic complexity (McCabe, 1976)

**What it counts (2+ sources, consistent):** for a control-flow graph with `E`
edges, `N` nodes, and `P` connected components, `V(G) = E − N + 2P` — for a
single function this reduces to one plus the number of decision points (`if`,
`while`, `case`, etc.). McCabe defined it as the number of linearly independent
paths through a program, and proposed it as a lower bound on the number of
test cases needed for full branch (not path) coverage. The primary 1976 PDF
itself could not be fetched (SSL failure on the one open mirror found); the
formula and its testing rationale are corroborated identically across roughly
six independent technical sources, so this is treated as settled despite the
fetch gap.

**Does it predict anything beyond size?** This is where the two available
replications disagree with the popular framing:

- **Shepperd (1988), one source, the founding critique:** argues CC rests on
  "poor theoretical foundations" and that for a large class of software it is
  "no more than a proxy for, and in many cases is outperformed by, lines of
  code." He also notes CC can *increase* when applying accepted
  structure-improving techniques, and that it weighs every decision equally
  regardless of nesting depth — the same blind spot cognitive complexity was
  later built to fix (§1, cognitive complexity below).
- **Landman, Serebrenik & Vinju (2016), one source, the large-scale
  replication:** ran CC-vs-SLOC correlation on 17.6M Java methods and 6.3M C
  functions and found the linear correlation is only **moderate**, weaker than
  most prior small-sample studies reported, because variance rises with method
  size. They also found that the strong correlations widely cited in older
  literature are largely an artifact of **aggregating** CC and SLOC over larger
  units — the correlation is a property of the aggregation, not of the
  per-method relationship.

**Two sources, same direction, different mechanism:** both conclude CC does
not cleanly separate from size, but for different reasons (Shepperd: it's
built from the same decision-counting a line count implicitly reflects;
Landman et al.: the correlation strength itself is an aggregation artifact).
Neither paper claims CC predicts *nothing* — the disagreement in the wider
literature is about how much information CC adds once size is already known,
and both these independent sources land on "not much, and less than commonly
believed."

### Cognitive complexity (SonarSource, 2017)

**One source — SonarSource's own white paper; no independent replication
found in this pass.** Read directly from the fetched PDF (via a text mirror,
since the original SSL-only URL wasn't fetchable in this environment). It is
explicit about what it changes and why:

- It gives a worked example: two methods that both score CC=4 — one with
  nested loops and conditionals, one a flat `switch` — and argues the nested
  one is "intuitively obvious" as harder to read, which CC cannot distinguish
  because it "over-valu[es] some structures, while under-valu[ing] others."
- **Not penalized:** method calls, null-coalescing operators, `else if`/`elif`
  chains (the mental cost is charged once), individual `switch` cases (charged
  once per switch, not once per case), and a run of the same boolean operator
  in one expression (charged once for the whole run, not once per operator).
- **Penalized, and penalized more when nested:** loops, conditionals,
  ternaries, `catch` clauses — nesting adds an extra increment on top of the
  structural one, which is the core departure from CC (CC is flat; cognitive
  complexity is nesting-aware by design).
- It also flags that CC has no rule at all for `try/catch`, a gap cognitive
  complexity closes.

This is a documented, principled fix for the exact failure mode Shepperd
described 29 years earlier (uniform weight regardless of nesting) — but it
remains a single vendor's own definition and marketing document; this pass
found no independent academic validation of the claim that it correlates
better with actual human comprehension than CC does.

### Halstead (1977)

**Corroborated by 3+ consistent secondary sources; primary book text not
accessible.** Counts distinct/total operators and operands (`n1, n2, N1, N2`)
and derives Volume (`V = N·log2(n)`), Difficulty, and Effort — vocabulary
size and usage, unrelated to control flow. No empirical replication of its
predictive validity was located in this pass; it appears here chiefly as an
input to the Maintainability Index below, not as a metric any source proposed
standalone.

### Maintainability Index

**Corroborated by 2+ secondary sources; primary Oman/Hagemeister/Coleman
papers not fetchable.** Combines Halstead Volume, CC, LOC and comment
percentage into one number; Microsoft's Visual Studio version is:

```
MI = MAX(0, (171 − 5.2·ln(HV) − 0.23·CC − 16.2·ln(LOC)) × 100 / 171)
```

**One critique, van Deursen (2014), read only via search snippets (403 on
direct fetch):** the constants 171, 5.2, 0.23, 16.2 come from fitting a small
1980s HP corpus (1,000–10,000 LOC, C and Pascal), and van Deursen reports no
published justification for them; the 100/171 rescale to a 0–100 band is
Microsoft's own addition, not in the original paper. Single source, not
confirmed firsthand — treat as reported.

## 2. CRAP, from its source

**Both foundational posts fetched directly — primary source, not secondhand.**

The original formula, from Savoia's July 2007 post:

```
CRAP(m) = comp(m)² × (1 − cov(m)/100)³ + comp(m)
```

**On the exponents — no stated calibration.** Savoia's own explanation for the
square on complexity is not a fitted constant but a boundary-case argument: at
zero coverage the formula reduces to `comp² + comp`, and he reads that as "if
you have no tests, your change risk increases, roughly, as the square of the
method complexity." He does **not** give a corresponding argument for the cube
on coverage in the fetched text — the steep coverage penalty is asserted, not
derived. Neither post claims empirical fitting of either exponent to defect
data; the formula is presented as v0.1, explicitly provisional, "input and
suggestions for the next version" invited.

**On the threshold of 30 — explicitly a guess, not a derived value.** From the
second post (Savoia & Evans, introducing crap4j): "After much debate, we
decided to INITIALLY use a CRAP score of 30" as the per-method threshold, with
5% non-compliant methods as the project-level tolerance. Both numbers are
presented as a starting point for calibration against real projects, not as
values with a stated derivation.

**On substituting testedness measures.** Neither fetched post mentions
mutation testing or mutation score as an alternative to coverage. The second
post is explicit that the authors know coverage is a weak proxy for test
quality — "Like all software metrics, CRAP is neither perfect nor complete,"
and it separately notes that high coverage doesn't guarantee good tests — but
the stated omission is design-level factors (cohesion, coupling), not a
different testedness input. The choice of `cov()` = line/branch coverage
appears to be a tooling-availability decision (crap4j reads JUnit + coverage
data) rather than a considered rejection of mutation score; the authors simply
don't discuss it in either fetched post.

**Later critiques — one source only, industry-level, not academic.** No
peer-reviewed critique of CRAP specifically was located in this pass (search
budget went toward primary CRAP sources and the complexity/AI questions
instead; this is a gap, not a finding of "no critiques exist"). The
GMetrics/JavaNCSS-adjacent tooling pages found treat CRAP as settled tooling
rather than critiquing the formula.

## 3. Complexity and AI-written code (2023–2026 evidence)

**Three independent primary sources, and they point in different directions
depending on task type — this disagreement is itself the finding.**

- **Generation vs. canonical (Dou et al. 2024, arXiv:2407.06153, one source):**
  across 3 closed + 6 open LLMs on standard benchmarks plus a new real-world
  benchmark, LLM-generated code is "shorter yet more complicated as compared
  to canonical solutions" — fewer lines, higher CC, similar API surface.
- **Transformation (arXiv:2504.14024, one source, n=30 corpus):** asked to
  transform/obfuscate existing Python functions, three LLMs (Claude-3.5-Sonnet,
  GPT-4-Turbo, Gemini-1.5) *reduced* CC on average (−1.27, −1.03, −0.47) rather
  than increasing it — "obfuscation by simplification." Different task from
  Dou et al. (transformation, not generation), so not a direct contradiction —
  but it means "LLM code trends more complex" isn't safe across task types.
- **Agentic iteration (SlopCodeBench, arXiv:2603.24755, Mar 2026, one source,
  read via third-party summary):** the source most directly answering "do
  metrics move under agentic iteration." 11 models each iteratively extended
  their own prior solutions across 93 checkpoints. **Structural erosion**
  (share of CC·√SLOC "complexity mass" in functions with CC>10) rose in 80% of
  trajectories; **verbosity** (redundant/duplicate code) rose in 89.8%.
  Against 48 mature open-source repos, agent code was "2.2x more verbose" with
  "substantially higher structural erosion" — human-repo metrics stayed flat
  over time, agent-code metrics worsened every iteration. Prompt interventions
  cut *starting* values 33–50% but not the *slope*: "trajectories remain
  parallel."

**One industry (non-peer-reviewed) source for corroboration:** GitClear's
2024/2025 reports, over 153–211M lines of real commit history, report CC
"generally higher" in LLM-assisted commits, alongside rising churn (5.7% of
new code reverted/edited within 2 weeks, up from 3.1% in 2020) and an 8x
jump in duplicate-block volume in 2024. Vendor research (GitClear sells
code-analytics tooling — a motive worth flagging) and not independently
replicated; treated as one directional data point, not a finding.

**Net read:** the strongest, most recent, and most directly relevant evidence
(SlopCodeBench) is single-source but methodologically the closest match to
"nightly trend series watching an agentic codebase over time" — it is a
trajectory study, not a snapshot, which is exactly the shape of question the
owner is asking. It should be weighted accordingly, with the caveat that it is
one paper, three months old at time of writing, not yet independently
replicated.

## 4. Gaming, in the literature

**No peer-reviewed study of metric gaming was located in this pass** — every
source found (SonarSource's own materials, NDepend, LinearB, Augment Code,
axify.io) is a vendor or practitioner blog. Consistent with each other, but
none independent of commercial interest in selling an alternative metric.
Treat the mechanisms below as industry-consensus description, not research:

- **Per-function CC deflation by function splitting:** consistently
  described — extracting a branch into a helper function moves the decision
  point out of the caller's CC count without removing it from the program's
  actual execution paths. Total path count across the module is unchanged;
  only the per-function attribution moves.
- **File/average dilution:** adding low-complexity boilerplate around
  high-complexity code pulls a file- or project-level *average* CC down
  without touching the worst function — a straightforward consequence of
  using a mean rather than a max or a distribution.
- **What cognitive complexity was built to resist:** per SonarSource's own
  white paper (§1), the nesting-increment design targets exactly this move —
  a deeply nested block moved into a same-level helper still costs a nesting
  increment. This is the vendor's stated design goal, not an independently
  tested claim that it resists splitting-based gaming in practice.

## 5. What this means for a trend series

**Recommendation: track cyclomatic complexity as the mutation-score-style
distribution metric (worst-N functions, not a mean), and pair it with a
verbosity/duplication signal rather than cognitive complexity or CRAP,
because the trend layer's job is watching a slope over time, not scoring a
single snapshot.**

Reasoning, weighed against what the evidence actually supports:

- **Cyclomatic complexity, not cognitive complexity, as the primary series.**
  Despite Shepperd and Landman et al. both finding CC correlates heavily with
  size, that isn't disqualifying for a *trend*: the mutation-score gate
  already catches "big and untested," so CC's job here is narrower — catching
  "concentrating decision logic" as a shape, exactly what SlopCodeBench's
  structural-erosion signal (CC·√SLOC concentration in high-CC functions)
  measures. Cognitive complexity is arguably the better per-function number,
  but it's a single vendor's proprietary definition with no independent
  replication found here — a risk for a metric this repo would trend for
  years.
- **Report a distribution, not a mean.** The LOC-correlation critique and the
  file-dilution gaming pattern point the same way: an average is gameable
  (dilution) and uninformative (it converges toward size, per Shepperd). Carry
  "% of functions above CC 10" or "share of complexity mass in the worst
  decile" — SlopCodeBench's own erosion metric, already validated against
  real agentic-coding behavior.
- **Don't adopt CRAP wholesale.** Its authors never claimed the exponents or
  the threshold of 30 were calibrated — they said so explicitly, twice, in the
  founding posts. This repo already has a real mutation score, a better
  testedness signal than the line/branch coverage CRAP was built around in
  2007. Substituting mutation score for coverage in a CRAP-shaped composite is
  defensible *by extension* of Savoia's own boundary-case argument (undertested
  code carries quadratic risk; mutation score is a stricter "actually tested"
  test than line coverage) — but that extension is this document's own
  inference, not something either source states, and should be labeled as
  such if it lands in an ADR. A verbosity/duplication counterpart is justified
  directly: it's the half of SlopCodeBench that moved *more* consistently than
  complexity did (89.8% of trajectories vs. 80%).
- **Where the evidence disagrees, that disagreement is the finding, not a
  reason to wait.** Generation-time LLM code trends more complex than
  canonical (Dou et al.), transformation-time LLM code trends less complex
  (arXiv:2504.14024), and agentic-iteration code trends toward concentrated
  complexity and duplication regardless (SlopCodeBench). A nightly series
  watching `stacks`'s own agentic-development history is the only way to learn
  which regime this repo is actually in.
