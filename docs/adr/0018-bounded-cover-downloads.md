# Bounded cover downloads: the magic-byte allowlist matters more than the size cap

A cover download carries a 15s abort, a 20 MB cap counted as the body streams, and a magic-byte allowlist of JPEG, PNG and WebP. `Content-Type` is checked but stays advisory, and absent is tolerated.

The cap stops a native decoder being handed 400 MB. The allowlist stops it being handed an *SVG* — not an image but a document, with its own parser and its own rules about external references, which sharp will otherwise rasterise happily. `Content-Length` is a claim, so the cap counts rather than trusting it.

## How this was decided

_Carried verbatim from the Decision Log this repository kept from July 2026, newest last._

- **2026-08-01** — **A gap disclosed indefinitely is a comment, which is the same thing an ungated rule is.** `SECURITY.md` had named the unbounded cover download by name for weeks — no timeout, no size cap, no content-type check before `sharp` — and an external pre-publication review found exactly that and called it the clearest remaining technical issue. It was reading the disclosure. Recording a hole is not the same as closing it, and this project's own standard says a rule nothing can fail on is a comment; that applies to the threat model too. Now gated as G18.

- **2026-08-01** — **The magic-byte allowlist matters more than the size cap.** A cap stops a decoder being handed 400 MB, which is real but dull. The allowlist stops it being handed an *SVG* — not an image but a document, with its own parser and its own rules about external references — which `sharp` will otherwise rasterise happily. Three signatures, JPEG/PNG/WebP, because those are what a cover arrives as; an allowlist rather than a denylist for the same reason `private:` fails closed, since a format nobody thought about must not be admitted by default. `Content-Type` is checked too but stays advisory and tolerates being absent, since some CDNs omit it and refusing on that would cost real covers; the bytes are what `sharp` parses, so the bytes decide.

- **2026-08-01** — **`Content-Length` is a claim, so the cap counts instead.** The header is checked first because refusing there transfers no body at all, but it is absent under chunked encoding and free to be wrong — so the body is read through a stream and abandoned the moment it passes 20 MB. `arrayBuffer()` cannot do this: it buffers everything before anything can measure it. Observed red at six of fourteen by restoring the old four-line `download`, and the streaming case did not merely fail — it ran **31 seconds** consuming a response that advertised 4 KB and never ended.

- **2026-08-01** — **One G18 test failed on arrival because the instrument was wrong, not the code.** "The body was never read" was measuring the test's own scaffolding: a default `ReadableStream` pulls once the instant it is constructed, to fill a queue of one. At `highWaterMark: 0` nothing is pulled until something actually reads. Worth logging because the failure looked exactly like the code not short-circuiting on `Content-Length`, and fixing the code would have been the wrong repair to a real red test.

- **2026-08-01** — **A gate made of stubs cannot see the one way this change breaks things, so the providers were asked directly.** Every G18 case stubs `fetch`, which is right for a gate and blind to exactly one regression: `cacheCover` treats every failure as "no cover" by design, so a provider answering cover bytes with `application/octet-stream` would now be refused *silently* and books would be logged bare with nothing going red. Checked live instead of assumed — Open Library `image/jpeg` (40 KB, `ffd8ffe0`), Google Books `image/png` (`89504e47`, and note the content endpoint serves PNG whatever the URL suggests), Apple `image/jpeg` (171 KB, `ffd8ffe0`); the largest is 0.8% of the 20 MB cap. That is a measurement with a shelf life, recorded with its date rather than as a property of the providers. It is also why `Content-Type` stays advisory and absent is tolerated: the bytes are what sharp parses, so the bytes decide.
