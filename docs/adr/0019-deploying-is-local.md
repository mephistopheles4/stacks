# Deploying is a local operation, and `deploy:site` publishes `main`

The vault is private, local and gitignored, so CI can only ever build the _fixture_ site. There is no deploy-on-merge, and every check that must happen before publishing happens in `pnpm deploy:site` — which runs the gates first, builds from the real vault last, re-checks the actual `dist/`, and refuses any branch but `main`.

After uploading it asks the live site which build it is serving, because a successful upload is not the same as a changed site. `SITE_URL` is required rather than optional: without it the build emits a relative `og:image` and the shelf arrives at the one moment it exists for as a bare URL.

## How this was decided

_Carried verbatim from the Decision Log this repository kept from July 2026, newest last._

- **2026-08-01** — **Deploying is a local operation, by construction.** The vault is private, local and gitignored, so CI can build the _fixture_ site and never the real one. There is no deploy-on-merge and the live site can drift from `main` with nothing enforcing otherwise — an honest consequence of local-first rather than something to engineer around. Every check that must happen before publishing therefore happens in `pnpm deploy:site`.

- **2026-08-01** — **The deploy re-checks the artifact, not just the code path.** `gate:public` proves the code cannot leak, using fixtures; it says nothing about the folder about to go on the internet. The pre-flight asserts the same properties against the real `dist/` — no private or wishlist books, no vault paths, no orphan covers, same-origin covers, an absolute `og:image` — plus an explicit check that _fixture titles are absent_, which is what catches the ordering trap directly rather than by implication.

- **2026-08-01** — **`SITE_URL` is required to deploy, not optional.** Without it the build emits a relative `og:image` and every link-preview scraper renders nothing, so the shelf arrives at the one moment it exists for as a bare URL. A deploy that silently produces that is worse than one that refuses.

- **2026-08-01** — **The script is `deploy:site`, not `deploy`, because `pnpm deploy` is a pnpm builtin.** The collision is not a warning — pnpm silently mangles the arguments. `pnpm deploy --dry-run` dropped the flag and went straight to uploading, and `pnpm deploy --help` invoked the script with a literal `"deploy"` argument. Found by a dry run that was not dry. Colon-namespaced like the other scripts, which have never collided for the same reason.

- **2026-08-01** — **wrangler runs via `pnpm dlx wrangler@4`, not as a devDependency.** CI never deploys, so adding it would put a large tree into every CI install and into `pnpm audit`'s surface for a tool that cannot run there. Pinned to a major so a deploy tool cannot silently change underneath a release.

- **2026-08-01** — **The pieces of one build expire together, or the build is incoherent.** Cloudflare Pages serves HTML and JSON with `max-age=0, must-revalidate` and images with `max-age=14400`. Every cover filename is a slug of a book title and is rewritten _in place_ by each deploy, so those two defaults leave the site serving a current `library.json` against covers up to four hours old. That is not just stale: `coverAspect` is measured from the file the build staged and the shelf draws each cover at that ratio, so new metadata against old bytes renders books at the wrong shape. Found the hard way — the mobile-crash fix deployed successfully, the deployment URL served the resized covers, and the custom domain kept handing out the 437 KB originals with nothing reporting a problem. `_headers` now makes `/covers/*` and `/og.png` revalidate like everything else; ETag keeps that cheap, since an unchanged cover costs a 304 rather than a re-download. Checked by `pnpm gate:public`, observed red.

- **2026-08-01** — **Half of that fix lives in a dashboard, and the repo cannot see it.** `_headers` is honoured — `stacks-51z.pages.dev` serves `max-age=0, must-revalidate` for `/covers/*` exactly as written. `stacks.aymandiab.com` serves `max-age=14400` for the same file on the same deployment, because a **zone's Browser Cache TTL** overrides origin `Cache-Control` for the static extensions Cloudflare caches by default, and 4 hours is that setting's default. HTML and JSON escape it only because Cloudflare does not cache those extensions by default, so they pass through with the origin's headers — which is why the split looked like a Pages quirk and was not. Setting Browser Cache TTL to **Respect Existing Headers** (Caching → Configuration) is what makes the `_headers` rule visible to visitors. `pnpm gate:public` can only ever assert what the build _sends_; nothing in this repo can assert what the zone does with it, and pretending otherwise would be a gate that protects nothing.

- **2026-08-01** — **A deploy is not finished when the upload succeeds.** The 4-hour image cache meant `deploy:site` could report success while every visitor still got the previous build's art. The alternative fixes were a cache purge from the deploy script — which needs a Cloudflare API token with Cache Purge, a new credential for a personal project — or content-hashed cover URLs, which would change the `covers/<filename>` shape that the same-origin check, the orphan check and the pre-flight all match on. Matching the TTLs costs nothing and touches no security check, so that is the fix; hashed URLs remain the better answer if the 304s ever cost more than they save.

- **2026-08-01** — **The deploy's live check could not tell which build was live, so it stamps one.** It compared cover _bytes_, and covers are named after book titles and keep those names between builds — so a deploy that changes only code leaves every cover byte-identical and the check reports a clean site whichever build the origin is serving. Observed, not theorised: minutes after a successful upload it said "the site is serving this build" while `index.html` still pointed at the previous bundle and a phone-viewport check read the old renderer's numbers straight back. Every build now writes `<meta name="stacks:build">` into the page, hashed from `index.html` and `library.json`, and the check asks the origin which build it has. **Not for reproducibility** — `library.json` carries the moment it was generated, so `dist/` never had that property and the stamp must not claim it; what a match means is that the origin is serving the bytes just uploaded, and nothing weaker. Byte-comparing the whole page was the alternative and is worse: any edge transform a zone might enable rewrites markup, and the check would then fail forever for a reason unconnected to deploying. A meta tag survives all of them. The injection is **asserted rather than assumed**, because a stamp that silently failed to land would make every future deploy fail its own check for a reason nobody would guess. And it waits out propagation — a deploy is not live the instant wrangler returns, and a check that cries wolf every time is a check that gets ignored.

- **2026-08-01** — **`--check-only` exists because a check you can only run by deploying is a check nobody watches fail.** It asks the origin which build it is serving and stops — no gates, no build, no upload — reading the stamp back out of the `dist/` that was last published rather than recomputing one, since re-hashing a file that now _contains_ its own stamp yields a different value and would report a mismatch against a perfectly current site. It also skips the pre-flight, which is about an artifact it is not publishing and one of whose assertions cannot hold under it: the og:image check compares the built page against the current `SITE_URL`, which is exactly what you change to point the check at a local server. That is how all three outcomes were observed rather than assumed — a match, a mismatch retrying and then warning, and a `dist/` with no stamp at all — and it is how the one real bug in the change was found: `const PROPAGATION_ATTEMPTS` declared beside the function that used it, which `--check-only` calls from the middle of the file, where a `const` has not initialised yet. Hoisted to the top with the rest of the configuration.

- **2026-08-01** — **`deploy:site` publishes `main` and refuses anything else — G17.** Making worktrees easy is what makes this reachable: the Decision Log's "deploying is a local operation, by construction" was written when there was one checkout, so _which branch_ answered itself by standing somewhere. Four checkouts on four branches, all reading the one shared `.env`, all holding `SITE_URL`, and the command is identical from every one. That log entry also already accepts the live site drifting from `main` — but that is about _when_ you deploy, not about publishing an unreviewed branch to the address people have. Same asymmetry as `private:`: refusing wrongly costs one flag, publishing wrongly is live and may already have been crawled. `--any-branch` is the override, named so it cannot be typed by accident; `--dry-run` and `--check-only` are exempt because neither uploads. The check runs _before_ the gates, since a refusal that arrives after two minutes of them is one people learn to pre-empt with the override.

- **2026-08-01** — **The guard is driven through the real script, both ways, not unit-tested in isolation.** A rule extracted into a testable function and then not wired in is the exact failure this repo's reverse-asserts exist for, so G17 spawns `scripts/deploy.ts` and reads what it says. `STACKS_VAULT` is pointed at nothing so the run always stops one check _after_ the branch decision — which means the gate can tell "refused" from "allowed" without ever building, staging or reaching the network, and works the same on a machine with a real deploy configured as on CI with no `.env`. The pass-on-`main` direction was observed from a worktree actually checked out on `main`, since `main` was not checked out anywhere at the time. Observed red by disabling the guard: three of five checks fail, including the one asserting `--any`, `--branch` and `--anybranch` are _not_ the override. An escape hatch you can stumble into is not one.
